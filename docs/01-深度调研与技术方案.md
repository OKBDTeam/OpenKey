# OpenKey（开门输入法）立项深度调研与技术方案

- 调研日期：2026-10-13
- 调研方式：四路并行专项调研（市场格局、五端平台约束、跨平台架构、功能模块专项）+ 主线交叉验证，信息来源以官方文档、GitHub 仓库与权威行业报告为主，采集时点均为 2026 年 10 月
- 目标：验证"五端一套仓库、原生框架开发、分阶段落地"的可行性，给出技术选型与实施路线

## 0. 执行摘要

**结论先行。** 本次调研的核心判断如下，依据与细节见后文各章。

1. **项目定位成立，存在真实空白。** 中国第三方输入法活跃用户超 7 亿，商业格局三强寡占（搜狗/百度/讯飞合计约 82%），但用户对广告与隐私的不满长期存在（新浪财经投票中 95.86% 用户不接受输入法广告）；开源阵营 Rime 生态五端割裂、无内置云同步，iOS 端主力"仓输入法（Hamster）"已闭源并长期停滞。"开源、隐私自托管、五端一致体验、内置云同步"四要素俱全的产品，目前不存在直接竞品。

2. **"一套代码五端"必须重新定义。** 输入法是深度绑定平台 API（Application Programming Interface）的应用类型，五端不存在统一的 IME（Input Method Editor，输入法编辑器）框架。已被 Rime 全家桶、Keyman、Bitwarden、1Password 反复验证的现实路径是：**核心引擎与业务逻辑一套代码（C++/Rust），五端各配一层原生薄壳**。这是"一套仓库"能达成、而"一套 UI 代码"不能达成的诚实边界。

3. **推荐核心架构：librime + Rust 服务核心 + 五端原生壳。** librime（Rime 输入法引擎，BSD-3 许可）是唯一经过五端大规模验证的开源中文引擎，绑定成本可控（iOS 仓输入法的 Swift 封装层仅约 280 行）；Bitwarden 客户端逻辑、同步引擎、加密、图床抽象、ASR（Automatic Speech Recognition，自动语音识别）调用等"引擎外"功能，建议以 Rust 编写为独立服务核心，经 C ABI 供五端绑定。Flutter/React Native/Compose Multiplatform 做键盘本体在 iOS 上不可行（键盘扩展内存硬限制约 60MB，此类框架运行时即超限）。

4. **iOS 是最大的约束源，必须在产品设计阶段就接受功能降级。** iOS 键盘扩展（Keyboard Extension）存在五条绕不过的硬限制：内存上限约 48–70MB；无"完全访问（Full Access）"权限时无网络、无共享容器；**无法向宿主 App 插入图片**；**密码安全输入框会强制切换回系统键盘**；**键盘内无法访问麦克风**。因此图片表情、密码填充、语音输入在 iOS 上都必须走替代路径（详见 2.3 节降级矩阵）。

5. **密码管理模块技术上可行，且各端路径清晰。** Bitwarden 的 REST 协议公开稳定（第三方客户端 rbw、Goldwarden、Vaultwarden 服务端均已验证可自行实现），加密规范文档完备，无需依赖其未授权的官方 SDK。"逐字键入模拟"在 Android/iOS 上就是 IME 的原生输入通道（天然合规）；Windows 端 SendInput 是带注入标志的合成输入，需数字签名与节流策略应对安全软件误报；macOS 密码框受 Secure Event Input 保护，应以复制到剪贴板为主路径。**目前市场上没有任何输入法内置密码管理器，这是蓝海差异化，但 iOS 端需以"主 App + 系统密码填充扩展"形态实现，不能只靠键盘。**

6. **云同步建议 WebDAV + 条目级合并，而非 Git 或 CRDT。** WebDAV 协议简单（核心仅 5 个动词），Rust 自研薄客户端工作量小；坚果云是国内唯一稳定的个人 WebDAV 服务。合并模型推荐"条目级 LWW（Last-Writer-Wins，后写者胜）+ HLC（Hybrid Logical Clock，混合逻辑时钟）+ 墓碑记录（tombstone）"，对词库/短语/设置这类数据足够且实现简单；CRDT（Automerge/Yjs）对本场景过重。自托管同步服务可后置为"单二进制 + SQLite"的官方组件。

7. **语音输入选型 sherpa-onnx，但 iOS 键盘内不可行。** sherpa-onnx（Apache-2.0）提供官方 C/Swift/Kotlin/Flutter 等十余种语言绑定，流式中英双语 zipformer 小模型 int8 量化后约 40MB，可在桌面与 Android 端本地实时运行；iOS 键盘扩展无麦克风且内存受限，语音必须跳转主 App 录音或走云端 ASR。AI 纠正润色建议设计为"用户可配置的 OpenAI 兼容端点"，与行业通行做法一致。

8. **词库许可有一条红线：rime-ice（雾凇拼音）为 GPL-3.0，不能随非 GPL 客户端默认内置分发。** 合规路径是"应用内运行时下载（用户触发导入）+ 自建 CC0 基础词库"；搜狗细胞词库等商业词库存在版权风险，只能作为用户个人转换导入（可集成 imewlconverter 思路提供工具）。

9. **建议按 8 个阶段实施**：基建 → 基础拼音输入 → 用户数据层 → 云同步 → 密码管理 → 表情图床 → 语音输入 → 官方云服务。排序依据是依赖关系（数据模型先于同步、同步先于密码库）、平台风险隔离（iOS 降级方案不阻塞其他端）与商业优先级（差异化核心尽早）。语音模块相对独立，可与第 3 阶段起并行启动。

10. **需要正视的两类成本**：一是五端维护成本（平台 API 每年都在变动，本次调研已实证 macOS 26 与 iOS 26 的行为变化）；二是分发合规成本（Windows 代码签名证书、Apple 开发者账号、Google Play 数据合规审计、Linux 发行版打包），其中 macOS 输入法无法上架 Mac App Store（Apple DTS 官方确认），必须走 Developer ID 签名 + 公证分发。

## 1. 市场调研

### 1.1 商业输入法格局（2025–2026）

**规模与集中度。** 据 MobTech 研究院《2025 年中国第三方输入法行业洞察》与艾媒咨询 2025 年数据（经行业报告汇总）：中国第三方输入法活跃用户规模突破 7 亿；搜狗输入法市占率 42.3%（MAU 约 4.2 亿）、百度输入法 31.5%（MAU 约 3.8 亿）、讯飞输入法 12.8%（MAU 约 3.1 亿），三强合计超过 82%；纳入微信输入法后的头部市占率达 84.4%（2025 年三季度）。行业呈典型寡占格局，但 2025 年下半年起格局开始松动。

**AI Native 新变量。** 字节豆包输入法（依托 Seed 语音大模型，上线三个月在 18–30 岁用户渗透率突破 15%）、阿里千问输入法、蚂蚁灵光相继上线，以"AI 原生"打法冲击传统格局；腾讯则维持搜狗 + 微信输入法双产品卡位。用户需求侧，AI 语音输入使用率 40.9%，74.7% 的用户希望输入法提供上下文感知的润色与补全（MobTech 调研）。**"AI 能力"已成为输入法竞争的第一变量，OpenKey 规划中的 AI 纠正润色模块方向正确，且应保持 LLM 端点可配置（对接任意供应商）以跟进模型迭代。**

**商业模式与用户痛点的结构性矛盾。** 输入法行业收入以广告与导流为主，而用户容忍度极低：新浪财经发起的投票中 95.86% 的用户不接受输入法插入广告。搜狗 2016 年被曝以明文 HTTP 上传用户打字内容（输入内容回传服务器），该事件至今仍是"输入法隐私焦虑"的标志性案例；2026 年搜狗启动全端广告治理，累计下线 20 余个广告位，侧面印证广告模式的式微。**开源 + 隐私自托管 + 无广告，正对准这一结构性矛盾。**

**微信输入法是最重要的产品参照系。** 其"隐私保护模式（默认，全本地）/ 拼写 Plus 模式（云端增强）"双模式设计，将"是否上传"的选择权交给用户，且明确承诺基础输入不注册不登录即可使用——这一设计值得 OpenKey 直接借鉴（对应到 OpenKey 即：本地模式零账号零上传，云同步/Bitwarden/AI 全部为可选增强）。跨设备能力方面，微信输入法支持跨设备复制粘贴（含图片）、词库与常用语同步、换机助手，采用"匹配码关联设备 + 加密上传服务器中转"方案，不强制登录账号——验证了跨端同步是真实高频需求，同时其鸿蒙版已接入 DeepSeek-R1/Hunyuan-T1 提供"问问 AI"。**注意：微信输入法的同步是封闭云（腾讯服务器），用户无法自选存储位置，这正是 OpenKey"用户自持服务器（WebDAV/自托管）"的差异化空间。**

### 1.2 开源输入法格局

**Rime 生态是开源中文输入的事实标准，但"发行版"模式导致五端体验割裂。** librime 引擎（BSD-3）之上，五端各有独立发行版、独立仓库、独立配置习惯：

| 发行版 | 平台 | 技术栈 | 状态 |
|---|---|---|---|
| 小狼毫 Weasel | Windows | TSF DLL + 独立服务进程（WeaselServer）+ C++ | 活跃维护 |
| 鼠鬚管 Squirrel | macOS | IMKit + Objective-C/C++ | 活跃维护 |
| fcitx5-rime | Linux | fcitx5 addon + C++ | 活跃维护 |
| 同文 Trime | Android | InputMethodService + JNI | 维护中，更新缓慢 |
| 仓输入法 Hamster | iOS | Keyboard Extension + Swift（RimeKit 三层桥接） | **已转闭源商业维护，GitHub 仓库自 2024 年起长期停滞（约 17 个月无有效更新）** |

**关键发现：iOS 端开源中文输入法实质断档。** 仓输入法闭源后，iOS 上已无可维护的开源全功能拼音输入法（App Store 在售版本为闭源商业软件）。开源社区对此普遍不满，这正是 OpenKey 进入的黄金空位。

**Rime 多端同步的现状是一面镜子。** Rime 自带"用户数据同步"机制：基于 installation_id + sync_dir 的设备快照（userdb.txt）文本合并，**只覆盖用户词频，不覆盖用户词典与自定义短语，且需手动触发**。社区为此拼出了大量高摩擦方案——iCloud Drive + macOS 软链接 + Hazel 监听 + iOS 快捷指令 + LaunchBar 定时脚本（详见 utgd.net 与 GitHub 社区 wiki 的多篇教程），Windows 端还需安装 iCloud 客户端将小狼毫用户目录指向 iCloud 路径。**结论：没有任何 Rime 发行版内置"配置 + 词库 + 短语 + 剪贴板"的一键自动云同步。把 sync_dir 抽象为 WebDAV/自托管服务并在客户端内置合并引擎，是 OpenKey 最直接可感知的差异化能力。**

**其他值得关注的信号。** fcitx5 本体（Linux）持续活跃；Android 上 AnySoftKeyboard（隐私优先）与 FlorisBoard（拉丁为主）长期维护但均无中文智能拼音能力；Linux 社区 2026 年出现了 RakuRaku IME 等小型新项目（Jetpack Compose 构建、全离线、GPL-3.0），佐证"隐私 + 离线"路线在海外应用商店同样有受众。

### 1.3 功能先例扫描

| 功能方向 | 市场先例 | 对 OpenKey 的启示 |
|---|---|---|
| 输入法内置密码管理器 | **无先例**。Bitwarden/1Password 是"密码管理器附带键盘"，方向相反 | 蓝海；但需吸收 Bitwarden iOS 的 Credential Provider 架构经验（密码管理器主 App 形态已验证） |
| 表情包/斗图 | 搜狗表情、百度斗图、微信输入法表情联想均有先例 | 候选词联想触发表情的交互已被市场教育；但"自定义图床 + 链接化输入"无先例 |
| 跨设备剪贴板 | 微信输入法已产品化（含图片） | 需求已验证；加密与 TTL（Time To Live，过期时间）设计可后发优势 |
| 词库/常用语云同步 | 微信输入法（封闭云）、Gboard（Google 账号） | 自托管同步是空白 |
| 语音输入 + AI 纠正 | 讯飞（口碑标杆）、豆包（Seed 大模型）、微信输入法（上传云端识别） | 桌面/Android 本地开源 ASR 可对标讯飞基础能力；AI 纠正润色走可配置 LLM 端点 |
| 无广告 + 开源 | 无一主流产品 | 直接对标微信输入法的"简洁无广告"口碑与其形成错位竞争 |

### 1.4 市场空白与生态位判断

1. **"开源 + 五端统一体验"空白**：Rime 体验割裂且 iOS 断档；单仓库统一产品只有 Keyman（SIL International，MIT 许可，覆盖 Win/macOS/Linux/Android/iOS/Web，但其定位是少数民族语言键盘布局而非智能拼音引擎）这一非直接可比先例——不过它证明了"monorepo + 共享核心 + 五端原生壳"在工程上完全可行。
2. **"自托管/用户自持服务器"空白**：所有云能力（微信、Gboard、搜狗）都是厂商封闭云；面向隐私敏感人群与"数字自托管"社区（NAS、VPS 用户）的输入法不存在。
3. **"输入法 + 密码管理"组合空白**：无先例，具备话题性与独特价值主张；技术上可行（见 4.2），需重点管理 iOS 降级预期。
4. **"创作者向图片表情"空白**：图床上传工具（PicGo 等）与输入法之间没有打通的先例；论坛等不能贴图的场景以 Markdown/BBCode 链接输入是真实痛点。
5. **时间窗口判断**：AI Native 新玩家（豆包/千问）主打 AI 对话与语音，但均为封闭云 + 大厂数据生态；OpenKey 的"隐私 + 自托管 + 开源"与之错位，窗口期在于趁大厂 AI 战争夺目之时，占住"可信输入"生态位。

## 2. 五端平台技术约束

### 2.1 五端技术约束对照表

| 维度 | Windows | macOS | Linux | Android | iOS |
|---|---|---|---|---|---|
| IME 框架 | TSF（Text Services Framework） | IMKit（InputMethodKit） | fcitx5 addon | InputMethodService | Keyboard Extension |
| 开发语言 | C++（COM 组件） | Swift / Objective-C | C++ | Kotlin | Swift |
| 形态 | **进程内 COM DLL** + 建议独立服务进程 | 独立进程（.inputmethod Bundle） | fcitx5 守护进程加载的共享库 | App 进程内 Service | App 扩展进程（与主 App 分离） |
| 内存/沙盒 | 随宿主 App 容器（UWP 内无网络则 IME 也无网络） | App Sandbox + 特殊 entitlement | 无特殊限制 | 常规 Android 进程 | **jetsam 硬限制约 48–70MB（实测 ~60MB），超限静默击杀** |
| 网络 | IME DLL 受宿主容器限制 → **网络功能必须放独立服务进程** | 正常 | 正常 | 正常（需申请权限） | **默认无网络，需用户手动开启 Full Access** |
| 向宿主输入图片 | 剪贴板 CF_DIB + 模拟 Ctrl+V（SendInput） | NSPasteboard + 模拟 Cmd+V | X11 可（ydotool/XTEST）；Wayland 受合成器策略限制 | commitContent（API 25+），需宿主声明 contentMimeTypes，多数 App 不支持 → 常用"复制到剪贴板"降级 | **无公开 API，硬限制**；仅可写剪贴板（需 Full Access）+ 引导用户手动粘贴 |

### 2.2 分平台要点

**Windows。** 微软已系统阻止基于 IMM32 的旧式 IME，TSF 是唯一合规路径。开发语言为 C++ COM，社区有现代参考实现（Khíín 项目以 C++17 + C++/WinRT 工具重写 TSF 层，README 明言"微软文档在多处不精确或过时，需要参考至少半打开源 TSF 输入法"——小狼毫、mozc、VietType 等被列为参考）。两个关键架构结论：其一，**TSF IME 是进程内 DLL，随宿主 App 的容器与权限运行**（微软官方文档明确：宿主 App 未声明网络权限时 IME 也无法联网），因此词库在线更新、云同步、Bitwarden 网络栈必须置于独立服务进程（小狼毫的 WeaselServer 命名管道 IPC 模式正是如此，可直接借鉴）；其二，**SendInput 合成输入自带 LLMHF_INJECTED 标志**，银行/企业 EDR（Endpoint Detection and Response，端点检测与响应）与反作弊系统可据此拦截，密码键入模块须"TSF 直接提交优先、SendInput 后备、键入间隔随机化"，且必须配置 Authenticode 代码签名。

**macOS。** IMKit 未被弃用，但属于"祖产级"框架（macOS 10.5 时代产物，早于 ARC/Sandbox/Swift），与 Swift 6 严格并发模型不兼容；社区已有成熟现代化方案 IMKSwift（唯音输入法 vChewing 项目产出）。踩坑点（来自 2026 年社区开发规范）：输入法 Bundle ID 必须含 `.inputmethod.`；`InputMethodConnectionName` 必须为 `$(PRODUCT_BUNDLE_IDENTIFIER)_Connection`（否则开 Sandbox 后无法加载）；应启用 App Sandbox 并声明 `mach-register` 例外；避免使用系统 IMKCandidates 候选面板（macOS 26 存在渲染缺陷），自建 SwiftUI/AppKit 候选窗；输入法进程无法断点调试（会冻结宿主 App），需以"核心库 + 薄包装"结构用单元测试开发。**输入法不可上架 Mac App Store（Apple DTS 官方确认），只能 Developer ID 分发**——这在产品规划上意味着 macOS 端不存在商店分发选项。密码场景受 Secure Event Input（密码框激活时系统级键盘加密）保护，第三方注入会被阻断，主路径应为剪贴板 + 引导粘贴。

**Linux。** fcitx5 是当前主流框架（2020 年重写，原生支持 Wayland 与 X11，附带 IM Bus 协议兼容 IBus 生态），**现代 Wayland 桌面下"独立发行 IME"已不可行**（无法可靠获知光标位置以定位候选窗），正确路径是编写 fcitx5 addon（InputMethodEngineV2 接口的 C++ 共享库，CMake 构建），发布为 fcitx5-openkey 包并进入主流发行版仓库。发行渠道建议 deb/rpm 官方仓库 + Flatpak（注意 Flatpak 沙盒需经 IM Module 通信）+ AUR。

**Android。** InputMethodService 是唯一输入通道；`InputConnection.commitText()` 逐字提交就是系统的官方输入方式——**OpenKey 密码"模拟敲击"需求在此端天然满足且零合规风险**。图片插入用 commitContent（API 25+），但宿主 App 必须声明 `contentMimeTypes`，实测多数 App 未支持，故通用降级路径为"复制到剪贴板 + 状态栏提示"。**高价值机会：一个 App 可以同时注册为 IME 与 AutofillService（API 26+）**——Android 11+ 支持 Inline Suggestions 将填充建议直接渲染进键盘候选条（Bitwarden 作为独立密码管理器已实现此联动，但尚无"输入法本体即密码管理器"的整合先例），这是 Android 端可做到超越 Bitwarden 键盘体验的点。合规红线：Google Play 于 2026 年 1 月更新政策，明确禁止 AccessibilityService 用于"自动登录其他 App"；数据安全表单需如实声明键盘数据采集（参考触宝 2019/2023 两次全线下架事件）。

**iOS。** 约束最多的一端，逐条列出（均为官方文档或 DTS 工程师确认级证据）：

- **内存**：jetsam 对键盘扩展的 phys_footprint 限制约 48–70MB（KeyboardKit 文档给出 60–70MB 区间；一线实测数据约 60MB；React Native 文档记录 48MB），**超限即被静默终止（无崩溃日志，键盘直接消失）**。词库必须采用内存映射（mmap）等手段压缩常驻内存，工程上将"键盘进程常驻内存 ≤ 40MB、峰值 ≤ 55MB"设为硬指标。
- **网络与容器**：未开启 Full Access 时无网络、无剪贴板读取、共享容器写入不可靠；**Full Access 必须用户在系统设置中手动开启**，且审核要求"基础打字功能在无 Full Access 时必须完整可用"。
- **图片**：键盘扩展无法向宿主 App 提交富内容（无公开 API），**图片表情只能"复制进剪贴板 + 引导粘贴"**，无法实现 Windows/Android 端的自动贴图。
- **密码**：`isSecureTextEntry` 的密码框**系统强制切换回系统键盘**，第三方键盘无法输入。正确架构（Bitwarden/1Password 已验证）：主 App 承载 vault（App Group/Keychain 共享数据），注册 **AutoFill Credential Provider Extension**（`ASCredentialProviderViewController`，AuthenticationServices 框架，iOS 12+，passkey 支持 iOS 17+），在系统键盘的 QuickType 建议条或密码填充弹层中提供凭据。
- **语音**：键盘扩展**禁止访问麦克风**（即使开启 Full Access），SFSpeechRecognizer 在键盘内也不可用；语音输入必须跳转主 App 录音（经 responder chain `UIApplication.open` 拉起主 App——Apple DTS 确认此行为合规；注意 iOS 26 起该调用需 Full Access）或走云端 ASR。
- **审核**：App Review 条款 4.4.1 要求键盘必须含切换输入法的地球键（无实体地球键设备上）、不得启动除设置外的其他 App、传输数据必须说明用途。

### 2.3 iOS 功能降级矩阵（产品预期管理）

| 功能 | Windows/macOS/Linux/Android 形态 | iOS 实际形态 |
|---|---|---|
| 图片表情输入 | 自动贴图（Win/mac 剪贴板+模拟粘贴；Android commitContent） | 复制到剪贴板 + 引导手动粘贴；纯文本场景输出图片链接 |
| 密码填充 | 键盘内直接逐字键入（Windows SendInput 后备） | 主 App + 系统 AutoFill 建议条（系统键盘场景）；普通文本框可由本键盘逐字键入 |
| 语音输入 | 键盘/输入法面板内本地 ASR（sherpa-onnx） | 跳转主 App 录音后回填，或云端 ASR（需 Full Access） |
| 云同步 | 后台自动同步 | 仅在 Full Access 开启后可用；建议主 App 内同步 + 键盘读共享容器 |
| 剪贴板同步 | 完整 | 读剪贴板受 iOS 16+ 粘贴授权弹窗约束；写剪贴板可用 |

**产品策略建议**：iOS 端宣传口径应为"与主 App 联动的完整方案"而非"全功能键盘"；同时把"Full Access 引导"设计为首次配置向导的核心步骤（行业实践表明该开关转化率低，需要在设置向导内用图文化引导补偿）。

## 3. 总体架构与技术选型

### 3.1 "一套代码五端"的诚实边界

用户目标中"一个仓库一套代码"与"各端原生框架"存在结构性张力：IME 的候选窗、键事件处理、与宿主 App 的集成全部是平台私有 API，五端没有公共抽象层。经对 Rime 全家桶（五端四个独立仓库）、Keyman（单仓库五端 + Web）、Bitwarden/1Password（Rust 核心 + 各端原生）三类先例的验证，工程界共识是：

- **可共享（约 60–70% 代码量）**：输入引擎、词库数据结构与排序、用户词库、加密/密码协议栈、同步引擎、图床抽象、ASR 推理与后处理、所有纯业务逻辑——这些与 UI、与平台 IME API 无关。
- **必须每端原生（约 30–40%）**：IME 框架接入层（TSF COM / IMKit / fcitx5 addon / InputMethodService / Keyboard Extension）、候选窗与键盘 UI、系统权限与设置界面、密码填充的系统集成（Windows SendInput / iOS Credential Provider / Android AutofillService）。
- **跨平台 UI 框架（Flutter/RN/CMP）不适用于键盘本体**：实证依据是 iOS 键盘扩展约 60MB 的内存硬限制与"Flutter/RN 运行时无法装入键盘扩展"的大量失败记录；但**主 App 的设置界面**不属于键盘进程，可酌情采用跨平台方案（Bitwarden 移动端、1Password 8 均为跨平台 UI + Rust 核心先例）。为降低维护成本，本方案建议主 App UI 也走原生（Android 端 Jetpack Compose、iOS 端 SwiftUI、桌面端 WinUI 3 / SwiftUI / Qt），理由是五端设置界面的复杂度有限，原生成本可接受且体验最优。

**结论：采用"一套核心（C++/Rust）+ 五套原生薄壳"的单仓库（monorepo）架构。** 这同时满足"一个仓库"与"原生框架"两个要求，是唯一被业界反复验证的路线。

### 3.2 核心引擎选型：直接采用 librime

| 路线 | 评估 | 结论 |
|---|---|---|
| A. 直接采用 librime（BSD-3） | 五端发行版验证充分；Hamster 的 Swift 封装层仅约 280 行（C API → ObjC 桥 → Swift），绑定成本可控；schema 词库方案生态成熟（可直接兼容 rime-ice 等社区方案）；lua 插件机制提供引擎内扩展能力 | **推荐** |
| B. 分叉 librime 后改造 | 丢掉上游社区与词库生态，长期合并成本高 | 不推荐 |
| C. 自研引擎（Rust/C++） | 拼音切分 + 音节图 + N 元语法排序从零验证需数年，且第一版产品竞争力弱于成熟引擎 | 不推荐（可作为远期演进选项） |

librime 与"引擎外功能"（密码、同步、表情、语音）的共存方式：librime 只管"按键 → 候选 → 上屏"的输入管线；OpenKey 的功能模块不侵入引擎，在五端壳层与独立服务核心（Rust services）中实现，通过拦截/扩展候选流程（例如表情候选注入、密码专用模式切换）与引擎协作。仓输入法已实证此模式在 iOS 内存约束下可行。

### 3.3 推荐总体架构

```
┌─────────────────────────────────────────────────────────────────┐
│                        OpenKey Monorepo                         │
├──────────────────────────────┬──────────────────────────────────┤
│  core/                       │  （跨平台共享，一套代码）           │

│  │                           │  同步: WebDAV 客户端+合并引擎      │
│  │                           │  图床: 声明式模板上传器            │

绑定技术：librime 以 C API 形式消费（Windows/macOS/Linux 直接 C++ 或 C 桥；Android 经 JNI；iOS 经"C → ObjC → Swift"三层桥，照搬 Hamster RimeKit 模式）；Rust 服务核心以 C ABI 导出（可选 uniffi 自动生成 Swift/Kotlin 绑定，桌面端手写 FFI）；跨端本地存储统一 SQLite（iOS 键盘扩展经 App Group 容器访问，为社区验证过的标准做法）；密码学各端用原生实现（CryptoKit / Windows CNG / RustCrypto），Bitwarden 协议层用 Rust 统一。

### 3.5 Monorepo 组织与构建

单仓库多工具链已有充分先例（Bitwarden clients、FlorisBoard、fcitx5-android、Keyman 均为单仓库混合工具链）。建议结构：

```
openkey/

关键实践：core 以预编译产物（静态库/framework/AAR）形式被五端工程消费，CI 上先构建 core 矩阵再触发各端构建；librime 以 git 子模块或 vendored 子树固定版本。

## 4. 功能模块技术方案

### 4.1 基础拼音输入（Phase 1 核心）

- **引擎**：librime + 简体全拼 schema（结构兼容 rime-ice 方案，便于用户迁移）。
- **词库**：默认内置自建 CC0 基础词库（基础词 + 高频词，目标 20–40MB mmap 后常驻 ≤ 15MB，iOS 端重点优化字表与 Trie 索引的映射加载）；雾凇拼音等社区方案通过"应用内运行时下载"提供（规避 GPL 分发问题，见 4.6）。
- **五端键盘 UI**：Android/iOS 全键盘拼音布局 + 候选条；桌面端候选横条 + 数字键选词；统一交互规范（翻页键、中英切换、双拼可配置支持：自然码/小鹤/微软等，直接复用 rime 双拼 schema 生态）。
- **验收口径**：在微信输入法/Rime 用户常用场景（长句输入、中英混输、模糊音、错音纠正）下，首屏候选与 rime-ice 方案基本一致；iOS 键盘扩展常驻内存 ≤ 40MB。

### 4.2 密码管理（Bitwarden 集成 + 本地模式）

**协议与合规。** Bitwarden 客户端-服务端协议为公开 REST + OAuth2 密码授权（identity 端点登录、api 端点 sync 拉取），第三方客户端已有 rbw（Rust CLI）、Goldwarden 与 Vaultwarden 服务端长期验证；官方 bitwarden/sdk-internal 许可证限定官方客户端使用，**不可直接依赖，需按公开协议自行实现（clean-room 方式）**——工作量集中在 HTTP 层与加密层，参考先例充分。协议兼容性对 Vaultwarden 的支持必须列入测试矩阵。

**加密规范（自研客户端必须对齐）。** KDF 支持 PBKDF2-SHA256（默认 60 万次迭代）与 Argon2id；主密钥派生（email 归一化 + KDF）→ stretched master key 解密用户密钥；数据加密采用 EncString 格式（AES-256-CBC + HMAC-SHA256，`2.x|iv|ct|mac`）。RustCrypto 生态可完整实现，无需平台密码库（也便于五端一致性测试）。

**"仅本地"模式。** 不配置服务器时启用本地 vault：自定义 SQLite 容器 + 同一套 EncString 加密方案（主密码派生对称加密），并支持 Bitwarden 加密 JSON 导入导出——既保证数据主权，又保留随时迁移到 Bitwarden 服务器的路径。

**各端填充路径（"模拟敲击"的落地形态）。**

| 端 | 主路径 | 说明 |
|---|---|---|
| Windows | TSF 直接提交文本 | 在 IME 激活处逐字符上屏，与正常打字无差异；无焦点/特殊场景后备 SendInput（键入间隔随机化 30–120ms） |
| macOS | 复制到剪贴板 + 引导 Cmd+V | Secure Event Input 阻断注入；可选 CGEvent 逐键合成（需辅助功能授权，作为实验开关） |
| Android | 键盘 commitText 逐字键入 + AutofillService | 双通道：IME 内密码模式逐字输入；系统填充建议条（Android 11+ inline 渲染进键盘） |
| iOS | 主 App + AutoFill Credential Provider | 密码框自动切系统键盘，由系统建议条提供凭据；普通文本框内键盘逐字键入 |
| Linux | fcitx5 提交文本 | 同 Windows 逻辑；ydotool 备注受 Wayland 限制 |

**安全设计要点。** 输入法本质上是"受信的键盘记录器"，密码功能把安全责任提到了产品级：vault 加密密钥仅存于系统安全区（Keychain / Android Keystore / Windows CNG / libsecret）；自动锁定（可配置超时 + 切后台即锁）；剪贴板场景强制 TTL 自动清除；密码输入期间禁用云候选/剪贴板记录/用户词频上报（本地学习开关全局关闭）；Windows 代码签名 + 尽早向主流安全软件厂商提交白名单申请以降低 SendInput 误报。

### 4.3 云同步（WebDAV + 合并引擎）

**存储后端。** 首选 WebDAV：协议核心仅 GET/PUT/MKCOL/PROPFIND/MOVE 五个动词，Rust 侧以 reqwest 自研薄客户端（含 Basic/Digest 认证、TLS、并发限速）即可，无需重型依赖；国内用户可即接坚果云（注意其免费配额与限频，需做节流与退避），国际用户接 Nextcloud/网盘生态成熟。**WebDAV 之外的补充路径**：自托管同步服务设计为"单二进制（Rust/Go）+ SQLite + /changes 增量 API"（参考 Obsidian 社区 SimpleSync/Selfsync 插件模式），作为后续官方云服务的同一套客户端抽象（client trait: webdav | selfhosted | official）。

**合并模型（"类 Git 融合"的正确形态）。** 逐文件级 Git 合并对移动端不现实（仓库体积、冲突 UI 成本）；CRDT（Automerge/Yjs）对词库场景过重且二进制格式不可读。推荐：**数据以"条目（entry）"为原子单位（词条/短语/设置项/表情项/剪贴板条目），每条携带 HLC 时间戳与设备 ID，同步引擎执行条目级 LWW 合并，删除以墓碑记录（tombstone）承载并设保留期（如 90 天）**。快照打包为版本化文件（JSON/二进制）经 WebDAV 分设备目录上传（`/openkey/sync/{device_id}/`，参考 Rime 的 installation_id 目录设计但自动化它），拉取他设备变更后本地三方合并。用户词频这类"只增不减"数据可用频次累加合并（Rime userdb 快照合并思路），保证 A/B 设备各自输入记录叠加不丢失。

**剪贴板同步。** 作为独立数据类型纳入同一同步引擎，但附加策略：端到端加密（vault 密钥或独立同步密钥派生，WebDAV 服务器只见密文）、条目 TTL（默认 24h）、条数上限（默认 100）、敏感值识别（正则匹配验证码/密码形态时本地警告）。

### 4.4 图片表情与图床插件

**插件形态：声明式模板 + 发版内置（与用户设想一致，且是合规最优解）。** 应用商店政策普遍禁止下载可执行代码（iOS 尤甚），因此"社区新增图床 → 下次发版内置"正是可行模式。落地为：图床模板 = JSON 声明（上传端点、认证方式（Bearer/Basic/自定义 header 模板）、multipart 字段名、响应链接的 JSONPath 映射、可选响应后处理）。该模板可覆盖 token 类图床（SM.MS、兰空 Lsky Pro、Chevereto、以图床模式使用的对象存储）的主流 API 形态；云厂商签名类（阿里 OSS/COS 直传签名）需内置 provider（Rust 核心实现签名算法），一并走发版内置。模板 JSON 本身支持应用内更新下发（属数据非代码）。

**图片格式策略（对原需求的一点修正建议）。** "上传时自动转换为 gif"经技术论证建议**默认不做**：主流表情源文件本就是 gif/webp/png，统一转 gif 只对静态图有意义，而静态图转 gif 会引入 256 色量化导致画质损失、体积膨胀，动图（webp/apng）转 gif 则是降级。建议：默认保留原格式，提供可选的"统一转 gif"开关（面向只接受 gif 的老论坛场景，Rust 核心内置 gif 编码，参考 gifenc 量级的轻实现），转换在桌面端执行为主。

**输入路径。** 表情项 = 图片文件（本地缓存）+ 关键字（多关键词触发候选）+ 远端链接（图床上传后回填）。候选触发：拼音关键字命中时在候选条注入表情项（复用 4.1 候选管线）；上屏动作按平台矩阵执行——Windows（写剪贴板 CF_DIB/文件 + SendInput Ctrl+V）、macOS（NSPasteboard + CGEvent Cmd+V）、Android（commitContent 优先，剪贴板降级 + Toast 提示）、Linux（X11 剪贴板 + 模拟；Wayland 视合成器）、iOS（剪贴板 + 引导粘贴）；纯文本场景（论坛发帖框等）上屏 Markdown/BBCode 链接（可配置模板）。

**官方表情库（远期）。** 官方仅维护"表情元数据列表（关键字 + 图床 URL，指向各大公共图床）"，客户端聚合加载与搜索，不存图片本体——与用户设想一致，技术上即"一个 JSON 清单 + CDN 缓存"，无新增难点。

### 4.5 语音输入与 AI 纠正润色

**开源 ASR 引擎对比。**

| 引擎 | 许可证 | 形态 | 中文效果 | 移动端资源 | 评价 |
|---|---|---|---|---|---|
| sherpa-onnx (k2-fsa) | Apache-2.0 | 流式 + 非流式均支持，官方 C/Swift/Kotlin/Flutter 等 12 种绑定 | 流式 zipformer 中英双语 int8 实测字准率约 90%+（社区实测 92% 级），可加载热词 | 流式小模型 int8 约 40MB，中端手机 RTF 远小于 1 | **推荐为默认引擎** |
| FunASR (Paraformer) | MIT（模型各自许可） | 服务端为主，paraformer 流式模型体积较大（数百 MB 级） | 中文最佳梯队 | 移动端偏重 | 官方云/自托管场景可选 |
| Vosk | Apache-2.0 | 流式小模型 | 中文模型老化 | 轻量 | 不推荐（被 sherpa-onnx 全面替代） |
| whisper.cpp | MIT | 非流式，tiny 起步 75MB+，大模型更重 | 中文可用但延迟高 | 移动端勉强 | 仅适合"录音后转写"场景，不适合实时输入 |

**结论**：桌面 + Android 采用 sherpa-onnx 流式 zipformer（int8 小模型）本地实时识别，模型文件经应用内下载分发（可更新）；**iOS 键盘内不可行（无麦克风 + 内存限制），iOS 方案为"键盘按钮跳转主 App 录音（系统 Speech 框架或 sherpa-onnx）→ 识别文本经共享容器回填键盘候选"或云端 ASR**；同时保留"用户配置云端 ASR 供应商"通道（讯飞/Gemini 等 API），形成三级能力（本地免费 / 系统级 / 云端付费）。

**AI 纠正与润色。** 识别结果流经可选的"纠正润色管线"：默认关闭；用户配置任意 OpenAI 兼容端点（base URL + API key + 模型名，与各开源工具通行的配置形态一致）后启用，prompt 设计为"修正 ASR 同音错字并轻度润色，保持口语结构，输出纯文本"。官方 AI 服务（远期）即同一管线的托管版。需注意键盘场景延迟预算：整句说完再纠错（非逐 token 实时改写），控制在 1–2 秒内。

### 4.6 词库与自定义内容

- **内置词库**：自建 CC0 基础词库（字表参照《通用规范汉字表》8105 字思路；词条以 CC0/自建来源起步），规避商业词库版权与 GPL 传染。
- **社区词库（rime-ice 等 GPL 方案）**：**不随客户端默认打包分发**（客户端若非 GPL，默认打包分发 GPL 词库存在许可证冲突风险），采用"应用内词库中心 → 用户点击 → 运行时从第三方源下载导入"路径，并在界面明示 GPL 来源与许可证——该模式与主流发行版对固件/非代码内容的处理惯例一致，且用户侧体验几乎无损。
- **商业词库转换**：搜狗细胞词库等仅供用户个人使用场景，提供"导入工具"（参考 imewlconverter 深蓝词库转换的转换思路，内置到桌面端管理器），明示版权提示（个人转换使用）。
- **在线词库更新**：词库中心统一管理订阅源（默认官方源 = 应用内更新服务/CDN，社区源可自定义 URL），支持定时更新（版本号 + 内容哈希校验）；桌面端服务进程与移动端主 App 执行更新，键盘扩展只读共享词库，规避 iOS 无网络问题。
- **自定义短语/证件号/地址/银行卡**：本质是 4.3 同步引擎中的一类条目（短语映射表，Rime custom_phrase 兼容格式），支持占位符（日期等）、敏感项加密存储（与 vault 同级加密），输入码触发直接命中候选第一位（优先级：自定义短语 > 用户数据 > 用户词典，与 Rime 生态习惯一致）。

## 5. 分阶段实施路线图

**排序逻辑**：① 每阶段都有可发布、可验证的交付物；② 数据模型先于同步（同步需要对象），同步先于密码（vault 需要 sync 基建）与表情（图床链接需要同步）；③ 语音模块相对独立，资源允许时可从 Phase 3 起并行启动；④ 官方云服务最后（商业化依赖前面所有模块的用户基座）。

| 阶段 | 名称 | 目标与范围 | 关键交付 | 依赖 | 主要风险 |
|---|---|---|---|---|---|
| **Phase 0** | 项目基建（约 1–2 月） | Monorepo 骨架、CI/CD、librime 集成、五端"Hello IME"（各端能弹候选窗）、签名与账号（Apple 开发者、Play、Authenticode 证书） | 五端空输入法可安装运行；core 交叉编译矩阵 | — | TSF/fcitx5 的工程门槛；证书采购周期 |
| **Phase 1** | 基础拼音输入（约 3–4 月） | 五端可用版：CC0 词库、候选 UI、中英混输、双拼配置、模糊音、iOS mmap 内存达标（≤40MB） | **首个可发布版本（0.9/1.0）**：全平台基础打字达到日用水平 | Phase 0 | iOS 内存调优；TSF 兼容性矩阵（各 App 逐类验证） |
| **Phase 2** | 用户数据层（约 1–2 月） | SQLite 数据模型（词条/短语/自定义内容/表情元数据/剪贴板）、管理 UI（五端设置内的词库管理器）、敏感项加密存储 | 自定义短语/证件号等可增删改并触发候选 | Phase 1 | 数据 schema 设计需前瞻（后续模块复用） |
| **Phase 3** | 云同步（约 2–3 月） | WebDAV 客户端 + LWW/HLC/墓碑合并引擎 + 分设备目录协议 + 剪贴板同步（E2E 加密/TTL）+ 同步冲突 UI | 两台设备词库/短语/设置/剪贴板自动融合一致 | Phase 2 | 合并正确性测试（多设备并发修改用例）；iOS Full Access 引导转化 |
| **Phase 4** | 密码管理（约 3–4 月） | 本地 vault（EncString 方案）→ Bitwarden 协议客户端（自建服务器地址/账户配置）→ 五端填充路径（4.2 矩阵）→ 安全审计 | "开门即密码管理器"：Android IME+Autofill 双通道、iOS Credential Provider、Windows TSF/SendInput、macOS 剪贴板路径 | Phase 1–3 | Windows 安全软件误报；Bitwarden 协议回归测试；安全责任（需渗透测试） |
| **Phase 5** | 表情与图床（约 2–3 月） | 表情管理（关键字/本地缓存）+ 图床声明式模板系统（首批内置 4–6 家）+ 贴图/链接双路径 + 候选注入 | 表情包用户可自建并可多端同步 | Phase 2–3 | iOS 贴图降级的产品表达；图床 API 差异化模板覆盖度 |
| **Phase 6** | 语音输入（约 2–3 月，可与 Phase 4/5 并行） | sherpa-onnx 集成（桌面/Android 本地流式）+ 模型下载管理 + iOS 主 App 录音回填方案 + AI 纠正润色管线（OpenAI 兼容端点） | 全端语音可用；AI 纠正可开关 | Phase 1（键盘管线）；可与 3–5 并行 | iOS 体验预期；模型体积与内存；识别准确率口碑 |
| **Phase 7** | 官方云服务（远期） | 账号体系 + 自托管同步服务同一套客户端抽象的官方托管版 + 官方表情库清单 + 官方 AI 管线托管 | 注册即用的云同步/表情库/AI | Phase 3–6 全量 | 运营与合规成本（备案/隐私政策）；商业模式设计 |

**里程碑建议**：v1.0（Phase 1 完成，"能打字"）→ v1.5（Phase 2–3，"五端一致 + 自同步"——此版本已具备对 Rime 用户的迁移吸引力）→ v2.0（Phase 4–5，"输入法 + 密码 + 表情"完整差异化形态）→ v2.5+（Phase 6–7）。

## 7. 结论与近期行动建议

**总体判断：项目可行，定位稀缺，但成功前提是接受"核心一套、壳层五套"的现实与 iOS 的功能降级矩阵，并把"密码管理"的安全责任当作产品级约束来管理。**

建议的启动顺序（未来 2–3 个月）：

1. **立项三件事**：确定开源许可证（两条候选路线：词库全部走运行时导入时，客户端可选宽松的 Apache-2.0；若计划内置分发 GPL 词库则客户端须 GPL-3.0 兼容——需在 Phase 0 形成正式法律决议）；注册组织账号（Apple Developer、Google Play、代码签名证书）；建立 monorepo 与 core CI 矩阵。
2. **先难后易验证**：优先做 Phase 0 的"五端 Hello IME"，其中 Windows TSF 与 iOS 键盘内存基线（空键盘实测 jetsam 预算）是最大的不确定源，最早拿到数据。
3. **以 rime-ice 兼容为词库策略起点**：Phase 1 直接支持导入 rime-ice 方案，立即获得 Rime 存量用户的迁移通道（这一人群正是"多端同步痛苦"最深的人）。
4. **差异化叙事**：对外表述建议强调"你的输入法，你的服务器"（自托管 + 隐私）与"开源五端一致"，将密码管理与表情作为 2.0 阶段的第二波传播点。
