### 0.2 决策记录（Decision Records）

**DR-001 许可证策略**
客户端整体采用 **GPL-3.0**；随客户端**默认内置分发的内容（词库、方案、字体、图标素材）一律 CC0/自制**。
- 影响：GPL-3.0 客户端使"用户导入 GPL 内容"（rime-ice 等）全程无许可证疑虑；但产品基调仍是"官方内置即 CC0"，因此 rime-ice 等 GPL 社区词库继续走"词库中心运行时导入"路径（见 5.6），不做默认内置。
- 附带决议：librime 为 BSD-3（兼容），OpenCC Apache-2.0（兼容），SQLite 公共域（兼容）；所有第三方依赖须在 `THIRD_PARTY_NOTICES.md` 登记，GPL/AGPL 依赖须经合并审查。

**DR-002 分发策略：近期不上架任何官方应用商店**
Windows/macOS/Linux/Android 通过**官网 + GitHub Releases 自行分发安装包**，并配套自建更新检查机制。
- 移除的工作项：Google Play 数据安全表单与政策合规、App Store 正式上架流程、商店审核应对。
- 保留（不因不上架而免除）的平台成本：Windows Authenticode 代码签名（自行分发时 SmartScreen 对未签名程序拦截更严）、macOS Developer ID 签名 + 公证（不公证则 Gatekeeper 直接阻断）、Android APK v2/v3 签名。
- **iOS 例外（必须明示的约束）**：iOS 在非越狱条件下不存在"下载安装包自行安装"的合法通道。近期方案为 **TestFlight 公测分发**：需要 Apple Developer Program 账号（99 美元/年），TestFlight 构建须通过 Apple 的 Beta 审核（键盘类条款 4.4.1 依然适用，见 4.5.6），且每个 build 有效期 90 天需持续滚动发版。不采用企业证书对外分发（违反 Apple 开发者协议）。据此 **iOS 排为最后一个交付端**：代码与桌面端同节奏开发，分发与推广延后。
- F-Droid 等社区仓库属可选远期项，不阻塞主线。

**DR-003 表情上传管线：统一转 gif + 上传前长边 400px 限制**
上传图床前执行：**等比缩放（长边 > 400px 时缩至 400px）→ 转 gif**。
- 产品依据：微信等应用将 gif 识别为"表情消息"整图发送不裁切；其他格式尺寸过宽/过长会被裁切。
- 原图保留在本地表情库；上传的是转换产物。参数（长边上限、体积警告阈值）可配置，默认值见 3.5。

**DR-004 语音引擎与模型运行时下载**
安装包**不携带** ASR 引擎与模型，用户开启语音输入时按平台下载"语音组件包"。
- Android：引擎 `.so` + 模型均运行时下载，动态加载（`System.load` 私有目录）。
- 桌面（Windows/macOS/Linux）：引擎动态库 + 模型作为可选组件运行时下载（安装器同时提供"包含语音组件"的可选勾选项，两者共用同一组件机制）。
- **iOS 例外**：Apple 政策（App Review Guideline 2.5.2）禁止 App 下载并执行可执行代码，因此 iOS 端引擎静态链接随包、仅模型运行时下载（模型属数据文件，合规）。该选择在"减少安装包体积"目标上对 iOS 打了折扣，属政策约束下的最优解。

**决策影响汇总**

| 决策 | 减少的工作 | 新增的工作 |
|---|---|---|
| DR-002 自行分发 | Play/App Store 合规、商店审核应对、触宝类政策风险 | 自建更新检查（4 端）、安装包签名体系、iOS TestFlight 滚动发版 |

## 1. 产品概述

### 1.1 产品目标

OpenKey 是开源五端中文输入法：基础拼音输入开箱即用；用户数据（词库/短语/表情/剪贴板/设置）经用户自持的 WebDAV 服务器多端同步；集成 Bitwarden 兼容的密码管理；支持自定义图片表情（图床链接化/贴图双路径）；集成开源语音识别并可选 AI 纠正润色。核心价值主张：**你的输入法，你的服务器**。

### 2.4 关键数据流

**输入管线（全部五端一致）**：
```
按键/触摸 → client IME 层 → openkey-ffi: ok_input_key(session, keycode)
→ rime-ffi: librime process_key → composition/candidates
→ client 候选渲染（表情/密码模式注入点：ok_get_candidates 后按模式过滤/追加）
→ 用户上屏 → ok_commit_text → IME 框架 API 提交宿主
```

**同步数据流**：
```
任意模块写入条目 → openkey-data: upsert(entry) + HLC 打戳 → oplog 追加
→ 同步调度器（客户端进程，见 4 章各端"驻留位置"）
   ① push：POST 本设备 oplog 增量 → WebDAV /devices/{id}/ops-N.jsonl
   ② pull：列出并拉取其他设备 oplog
   ③ merge：条目级 LWW / 词频累加 / 墓碑保留 90 天
   ④ apply：写回本地库 → 通知引擎重部署（词库类）
   ⑤ 惰性：每 24h 或 oplog > 4MB 时合并出全量快照并 GC 旧 oplog
```

**组件包数据流**：
```
用户开启功能 → 检查组件注册表 → 无则拉取 versions.json（GitHub Releases，可配镜像）
→ 下载 zip → SHA-256 校验 → 原子解压到 components/{name}/{version}/
→ 更新注册表与当前版本指针 → 加载（模型直接用；引擎 so 走平台加载器）
失败路径：校验失败→删除半成品并提示；旧版本保留可回滚
```

## 3. Core 层详细设计

### 3.1 openkey-rime-ffi（librime 封装）

- **初始化**：`ok_rime_setup(shared_data_dir, user_data_dir, app_name)` → librime `RimeSetup` traits；每个平台确定两个目录（见 4 章各端）。
- **会话**：每输入上下文一个 session id；`ok_input_key` / `ok_get_composition` / `ok_get_candidates(page)` / `ok_select_candidate(index)` / `ok_commit`。
- **方案管理**：`ok_set_schema` / `ok_list_schemas`；方案文件即 rime `*.schema.yaml`，OpenKey 主方案 `openkey.schema.yaml` 由 shared/schemas 提供并内置（CC0 词库的挂载点）。
- **userdb 同步快照**：包装 librime 的 installation.yaml + sync 机制——`ok_rime_sync_export()` 调用 librime 维护任务生成 `<dict>.userdb.txt` 快照到 `sync/{installation_id}/`；`ok_rime_sync_import()` 在快照拉取后触发 rime 合并与重部署。openkey-sync 以"特殊条目类型 rime_userdb"承载这些快照文件（见 3.3.4）。
- **插件**：构建期编入 librime-lua（方案生态兼容）；不编入 octagram/predict（体积考虑，词库中心可后续评估）。

### 3.2 openkey-data：数据模型（SQLite）

数据库文件：`openkey.db`（每用户一套，位于各端用户数据目录；iOS 放 App Group 容器）。敏感字段列级加密（密钥来自 vault 模块，见第 6 章）。

```sql
-- ① 统一条目表：所有可同步数据
CREATE TABLE sync_entries (
  key         TEXT PRIMARY KEY,      -- 条目 UUID（type 前缀 + ULID）
  kind        TEXT NOT NULL,         -- phrase|user_word|emoji_meta|clipboard|setting|rime_userdb
  payload     BLOB NOT NULL,         -- UTF-8 JSON；敏感字段在 JSON 内以 "enc$" 前缀密文呈现
  hlc         TEXT NOT NULL,         -- "物理毫秒.计数器.deviceId"，排序键
  device_id   TEXT NOT NULL,
  deleted     INTEGER NOT NULL DEFAULT 0,   -- 墓碑
  updated_at  INTEGER NOT NULL       -- 本地墙钟，仅供 UI 展示
);
CREATE INDEX idx_entries_kind ON sync_entries(kind, deleted);
CREATE INDEX idx_entries_hlc  ON sync_entries(hlc);

-- ② vault（Bitwarden 模型映射；不直接参与条目同步，走 Bitwarden 服务器协议；本地模式下由 sync 以整库密文快照条目同步）
CREATE TABLE vault_items (
  id          TEXT PRIMARY KEY,      -- Bitwarden cipher UUID（本地模式自生成）
  type        INTEGER NOT NULL,      -- 1=login
  name_enc    BLOB NOT NULL,         -- EncString 序列化
  data_enc    BLOB NOT NULL,         -- 加密的登录字段 JSON（username/password/uris/totp...）
  folder_id   TEXT,
  favorite    INTEGER NOT NULL DEFAULT 0,
  revision    TEXT,                  -- Bitwarden revisionDate
  deleted     INTEGER NOT NULL DEFAULT 0
);
CREATE TABLE vault_meta (            -- KDF 参数、服务器地址、账户、加密的用户密钥等
  k TEXT PRIMARY KEY, v BLOB NOT NULL
);

-- ③ 表情条目的 payload 结构（kind=emoji_meta，文件不入库）
-- {"keywords":["哈哈","hhh"],"file":"sha256.png","format":"png",
--  "remote":{"provider":"smms","url":"https://...","uploadedAt":1700000000000}}

-- ④ 组件注册表
CREATE TABLE components_registry (
  name        TEXT NOT NULL,         -- voice-engine / voice-model-zh / lexicon-rime-ice / imagehost-templates
  version     TEXT NOT NULL,
  status      TEXT NOT NULL,         -- installed|downloading|broken
  installed_at INTEGER NOT NULL,
  PRIMARY KEY(name, version)
);
CREATE TABLE components_current (name TEXT PRIMARY KEY, version TEXT NOT NULL);

-- ⑤ 设备注册（本机身份）
CREATE TABLE device_identity (
  id TEXT PRIMARY KEY,               -- installation UUID
  name TEXT NOT NULL                 -- 用户可读设备名
);
```

**词频数据的边界**：用户词频不进 `sync_entries`（它是 librime LevelDB userdb），同步引擎只搬运其快照文件（3.3.4）。

### 3.3 openkey-sync：同步引擎

#### 3.3.1 HLC 实现

- 结构 `{physical_ms, counter, device_id}`；接收远端条目时执行标准 HLC 合并算法（physical 取大、counter 相应推进），保证全序可比较且不依赖设备时钟可信。
- `new_hlc()` 单调递增；检测到本地时钟回拨 > 5s 时计数器补偿并记警告日志。

#### 3.3.2 远端目录布局（WebDAV）

```
/openkey/
├── manifest.json                    # {schema:1, owner_hint(明文设备名哈希), created}
├── devices/
│   ├── {device_id}/
│   │   ├── info.json                # 设备名、平台、last_seen_hlc
│   │   └── ops/
│   │       ├── 00000.jsonl         # oplog 分片，4MB 滚动
│   │       └── 00001.jsonl
└── snapshots/
    ├── {hlc}/entries-{shard}.json  # 惰性全量快照（新设备/灾难恢复用）
    └── {hlc}/manifest.json
```

oplog 行格式（JSONL，每行一条）：
```json
{"key":"phrase-01H...","kind":"phrase","op":"upsert","hlc":"1760000000123.4.win-abc",
 "enc":"gAAAA..."} 
```
`enc` 字段为 E2E 加密后的条目密文（见 6.3），WebDAV 服务器只见密文；`key/kind/op/hlc` 明文（元数据最小化）。

#### 3.3.3 同步状态机

```
idle ──(触发:手动/定时/开机/写后延迟)──▶ push ──▶ pull ──▶ merge ──▶ apply ──▶ idle
                                        │                          │
                                        └── 失败:指数退避(1m/5m/30m)─┘
并发写入：同步期间本地新写入正常追加 oplog，下一轮带上。
```

合并规则表：

| 数据类型 | 合并规则 |
|---|---|
| phrase / emoji_meta / setting / clipboard | 条目级 LWW（HLC 大者胜）；删除 = 墓碑，保留 90 天后 GC（GC 仅在所有已知设备 last_seen_hlc 超过墓碑时间时执行） |
| user_word（自造词） | LWW |
| rime_userdb（词频快照） | 频次累加合并（Rime 快照合并语义）：`freq(merged) = freq(A) + freq(B) - freq(共同祖先)`，共同祖先取双方快照中同 installation 的上一版 |
| 同 key 并发删除 vs 修改 | 删除胜出（墓碑 HLC 大者胜），并在冲突日志中记录被删内容摘要，支持 30 天内从快照找回 |

#### 3.3.4 rime userdb 适配器

- push 前：`ok_rime_sync_export()` → 得到当前快照文件 → 与上次导出快照 diff，无变化则跳过。
- pull 后：远端快照落盘到 `sync/{installation_id}/` → `ok_rime_sync_import()` 触发 rime 合并 + 重部署。
- 快照文件作为 kind=rime_userdb 条目走同一 E2E 通道。

#### 3.3.5 WebDAV 适配器与限频

- trait `SyncBackend`：`put/get/mkcol/propfind/move/delete`（即 3.7 节组件下载器也可复用其 HTTP 层）。
- 内置 WebDAV 实现（reqwest，Basic/Digest 认证、TLS、UA="OpenKey/{ver}"）；后续官方云/selfhosted 实现同一 trait。
- **坚果云适配**：默认节流——请求合并（每轮 sync 批量上传 oplog 与分片）、30 分钟窗口令牌桶 ≤ 1000 请求、失败退避；用户可自定义服务器则放宽。
- 同步调度：默认手动 + 开机后 5 分钟 + 写入后静默 10 分钟（可配"定时同步"档位：关闭/手动/10 分钟/1 小时）。

#### 3.3.6 剪贴板同步策略

- 条目 payload：`{text|image_ref, source_app?, created_at}`；图片剪贴板一期仅同步文本+表情引用（体积与隐私权衡），图片本地保留。
- TTL 默认 24h；上限 100 条；高敏识别（验证码/长数字串形态）默认不同步（可配）。
- 上传前 E2E 加密；接收端非焦点不弹通知，仅在剪贴板面板可见。

### 3.4 openkey-vault：Bitwarden 协议栈与本地 vault

#### 3.4.1 模块划分

| 子模块 | 职责 |
|---|---|
| kdf | prelogin 获取服务器 KDF 参数；PBKDF2-SHA256（默认 600k）/ Argon2id；主密钥派生 + stretched master key |
| enc | EncString 编解码（type2: AES-256-CBC+HMAC；预留 type7 COSE 兼容）；加解密、MAC 校验 |
| api | identity token（password grant + refresh）/ sync 全量拉取 / cipher CRUD（一期限：login 类型 + 读写） |
| local | 本地 vault：同 EncString 加密方案，主密码 KDF；导出 Bitwarden password-protected 加密 JSON（互通） |
| lock | 锁定状态机：Unlocked → SoftLocked（密钥仍在内存）→ Locked（密钥清除，需主密码/生物识别重解） |

#### 3.4.2 加密流程（与官方客户端语义一致）

```
master password + email(lowercased) ──KDF──▶ master key
master key ──HKDF-SHA256(stretch)──▶ stretched master key
stretched master key ──解密──▶ user key（64B = 32B enc key + 32B mac key）
user key ──解密──▶ 各条目 EncString；认证密码 = PBKDF2(pw, master_key, 1) 仅发服务器
本地模式：master password ──KDF──▶ local key ──加密整库（含 vault_meta 备份导出）
```

#### 3.4.3 兼容矩阵（M3 验收）

| 目标服务器 | 必须通过 |
|---|---|
| Vaultwarden（社区主流自建） | 全流程：登录/sync/增改/锁定 |
| bitwarden.com 官方 | 全流程 |
| 用户自指 URL | 允许任意 base URL（identity/api 分开配置） |

### 3.5 openkey-emoji：图像管线（DR-003）

#### 3.5.1 管线

```
源文件(png/jpeg/webp/gif)
  → 探测（是否动画）
     ├─ 静态图：解码单帧
     └─ gif 动画：逐帧解码（帧延迟保留）；webp/apng 动画：一期取首帧 + 界面提示"动画将取首帧"（二期补逐帧）
  → 缩放：长边 > MAX_EDGE(默认 400px) 时等比缩到 MAX_EDGE（Lanczos3）；小于则不放大
  → 量化：NeuQuant 256 色 + Floyd–Steinberg 抖动（默认开，防渐变 banding）
  → 编码：GIF89a（循环标记/透明索引/帧延迟）
  → 体积检查：> MAX_BYTES(默认 2MB) 时向 UI 返回警告（仍允许继续，由用户确认）
```

- 产物缓存：`emoji_cache/{key}/upload.gif`；原图存 `emoji_files/{sha256}.{ext}`（上传失败重试不重复转换）。
- 参数表（设置项，全部走 3.2 设置条目可同步）：`emoji.max_edge=400`（范围 200–800）、`emoji.dither=true`、`emoji.max_bytes_warn=2097152`。
- 依赖：`image` crate（PNG/JPEG/GIF/WebP 解码、Lanczos 缩放）+ `gif` crate（编码）。
- **转换执行位置**：表情上传发生在各端主 App/设置程序（键盘进程不执行图像管线）。桌面端与 Android 在主 App/设置程序内执行；iOS 在主 App 内执行（上传本身即主 App 行为，无需键盘参与，键盘扩展不链接图像管线模块——见 4.5.2 的编译期 feature 隔离）。

#### 3.5.2 上传状态机

`local_only（未上传）→ converting → uploading → uploaded(记录 provider+url) → failed(可重试)`；URL 生成后写入 emoji_meta 条目参与同步（其他设备获得"本地无文件但知道远端 URL"状态，可按需下载文件）。

### 3.6 openkey-voice：语音组件

#### 3.6.1 组件包格式

```
voice-engine-android-arm64-v1.10.0.zip
├── manifest.json      # {"name","version","platform","abi","files":[{path,sha256}],"engine":"sherpa-onnx","sherpa_version":"1.10.x"}
```

- 默认模型：sherpa-onnx `streaming-zipformer-bilingual-zh-en` small int8（batch=1 优化，约 40MB，RTF < 0.1，中文实测字准率约 90% 级，调研报告 4.5）；桌面端可另选更大的 zh 模型（组件中心列出）。
- 模型热词：预留 `hotwords.txt`（用户自定义），识别时传入。

#### 3.6.2 各端加载策略（DR-004 细化）

| 端 | 引擎二进制 | 模型 | 加载方式 |
|---|---|---|---|
| Windows | 可选组件（运行时下载 dll 或安装器勾选） | 运行时下载 | OpenKeyServer 进程 `LoadLibrary`（目录隔离，见 4.1.4） |

#### 3.6.3 识别会话生命周期

`VoiceEngine::create(model_dir, hotwords) → start_stream(pcm 16k mono) → feed(chunk) → on_partial(text) / on_final(text) → stop → destroy`。FFI 层暴露 C ABI；平台音频采集（16kHz/单声道/16bit，iOS 与 Android 采集参数对齐 sherpa 要求）由各端实现，经统一接口注入。

### 3.7 openkey-components：组件分发基建

- **清单源**：`versions.json`（结构见附录 B），发布于 GitHub Release（`components` asset）；用户可自定义镜像 URL（含国内可达性考虑）；**不做静默下载**，所有组件下载均显式经用户开启功能时触发。
- **完整性**：每组件 SHA-256；manifest 文件本身 GPG 签名（自行分发的供应链信任根，发布流程见 7.4），客户端内置公钥指纹。
- **原子性**：解压至 `components/{name}/{version}.tmp/` → 全部文件校验 → 原子 rename → 注册表登记；失败清理 tmp 并保留旧版本（回滚 = 切回 `components_current` 指针）。
- **共用者**：语音引擎/模型、词库包（含 rime-ice）、图床模板包。统一入口 `ok_component_ensure(name, callback) / ok_component_gc()`。

### 3.8 openkey-imagehost：图床模板引擎

#### 3.8.1 模板分层

- **Template（声明式，可热更）**：覆盖 token 类图床——上传端点、认证（header 名 + 值模板，支持 `{token}` 占位）、multipart 字段、响应 JSONPath。内置首发：SM.MS、兰空 Lsky Pro、Chevereto；模板随 components 机制更新（数据非代码）。

```json
{
```

## 4. 五端客户端详细设计

各端统一小节：进程模型 / IME 接入 / 与 core 绑定 / 平台特定设计 / 分发与更新 / 验证清单。

### 4.1 Windows

**4.1.1 进程模型**
- `OpenKeyTsf.dll`（TSF COM 组件，in-process）：仅做按键拦截、preedit/commit、候选窗定位与通信；**零网络、零重逻辑**（宿主容器约束，见调研报告 2.2）。
- `OpenKeyServer.exe`（常驻）：加载 librime + openkey 全部 core（rime 会话、同步调度、vault、组件下载、语音引擎）；与 TSF DLL 经命名管道 `\\.\pipe\openkey` 通信（WeaselServer 模式）；单实例锁；崩溃自动重启（TSF 侧重连）。**首次启动同样由客户端负责**：TSF 侧连接管道失败时从 DLL 同目录拉起 `OpenKeyServer.exe`（每进程一次，连接成功后重置），避免用户未手动运行服务即无法输入（v0.1.0 反馈，2026-10-17 补齐）。
- `OpenKeySettings.exe`（设置/管理 UI，WinUI 3 或先 WPF）：与 Server 通信展示词库中心、表情管理、vault、同步、语音设置。

**4.1.2 TSF 要点**
- 实现 `ITfTextInputProcessorEx / ITfKeyEventSink / ITfThreadMgrEventSink / ITfCompositionSink / ITfEditSession / ITfDisplayAttributeProvider / ITfCandidateListUIElement`；注册表注册（HKLM `CTF\TIP`），x64 + ARM64（x86 兼容视需求后置）。
- 候选窗：D2D 自绘窗口（跟随 caret，DPI aware）；参考实现：Weasel、tsf-sample-ime、Khíín（README 所列参考清单全部列入开发读物）。

**4.1.3 密码键入双通道（状态机）**
```
密码模式选定条目
 → 检测当前焦点上下文是否可用 TSF 提交
    ├─ 可用：逐字符 commitText（30–120ms 随机间隔）
    └─ 不可用（禁用 IME 的密码框/特殊窗口）：
       ① 提示用户并请求确认"模拟键入"
       ② 前台窗口句柄校验（GetForegroundWindow + 进程名白名单确认）
       ③ SendInput 逐字符（同样随机间隔；UTF-16 → 按键序列）
       ④ 失败（被拦截/焦点丢失）→ 中止 + 引导复制到剪贴板（TTL 45s）
键入完成 → 立即 SoftLock
```

**4.1.4 目录与语音组件**
- 安装目录 `%ProgramFiles%\OpenKey\`；用户数据 `%APPDATA%\OpenKey\`；组件 `%LOCALAPPDATA%\OpenKey\components\`（Server 的 LoadLibrary 搜索路径，不进 PATH）。
- 安装器：Inno Setup（WiX 二选一，倾向 Inno 起步）；Authenticode 签名（见 7.4）；安装器含"语音组件（可选，约 50MB）"勾选项。

**4.1.5 更新**：Server 每日检查 GitHub Releases `latest.json`（版本/哈希/签名），提示用户手动下载（一期不做静默自更新，下载链接直达）。

**4.1.6 验证清单**：全屏应用/游戏（独占模式）、UWP 沙盒（复制粘贴与提交）、RDP 会话、多显示器 DPI、CTF 崩溃恢复、密码框双通道全路径、360/火毒/Defender 拦截演练（SendInput 白名单流程）。

### 4.2 macOS

**4.2.1 进程模型**
- `OpenKey.inputmethod`（安装至 `/Library/Input Methods/`）：IMKServer + IMKSwift `IMKInputSessionController`；自绘候选面板（SwiftUI/AppKit，**不用系统 IMKCandidates**——macOS 26 渲染缺陷，见调研报告 2.2）；直接加载 openkey core（此进程承担同步调度与 vault，macOS 无容器网络限制）。
- `OpenKey.app`（主 App）：设置/词库中心/表情管理/vault 管理/录音/组件下载；与输入法进程共享 `~/Library/Application Support/OpenKey/` 用户目录（文件锁保证 SQLite 并发安全：WAL 模式 + busy_timeout）。
- 注意：输入法 Bundle ID 必须含 `.inputmethod.`；`InputMethodConnectionName = $(PRODUCT_BUNDLE_IDENTIFIER)_Connection`；App Sandbox + `mach-register` 例外（安装器按 IMKSwift 规范生成 entitlements）。

**4.2.2 键入与表情**
- 密码：主路径复制到剪贴板 + 引导 Cmd+V（TTL 45s 自动清除）；CGEvent 逐键合成为实验开关（默认关，需 Accessibility 权限，UI 明示 Secure Event Input 下无效）。
- 贴图：NSPasteboard 写图 + CGEvent Cmd+V；链接文本路径直出。

**4.2.3 分发**：Developer ID 签名 + notarytool 公证 + pkg 安装器（安装到 /Library/Input Methods 后提示注销重登）；官网/GitHub Releases 分发；Sparkle 框架做更新检查（一期同 Windows：提示手动下载）。

**4.2.4 验证清单**：CapsLock 切换 ABC/中文高频切换不卡（IMKInputController 实例风暴，参考 IMKSwift 文档）、Secure Input 场景提示、罗技/ Karabiner 虚拟设备兼容、公证通过率监控。

### 4.3 Linux

**4.3.1 形态**：`fcitx5-openkey` addon（`.so`，`InputMethodEngineV2`），配置文件 `openkey.conf`（Addon）+ `openkeypinyin.conf`（InputMethod 注册）；候选窗走 fcitx5 classicui（不自绘）。
- **进程内直跑 core**（fcitx5 守护进程内加载 openkey Rust so + librime）：Linux 无 AppContainer 类网络限制，且独立进程的收益低于复杂度（调研报告 2.2 结论）；addon 崩溃即 fcitx5 崩溃的风险以 core 测试覆盖率控制。
- 词库在线更新/同步调度：fcitx5 进程内定时器执行（WriteWatcher 触发重部署）。

**4.3.2 密码与贴图**：fcitx5 commit 逐字键入；剪贴板 `wl-copy`/`xclip` + ydotool/XTEST 模拟粘贴（Wayland 下模拟受限时降级为复制+提示）；vault 管理 UI 由 `openkey-config`（独立 GTK4/Qt 工具）承担。

**4.3.3 打包**：deb（PPA/官网 apt 源起步）+ rpm copr + AUR（社区）+ Flatpak（org.fcitx.Platform 基座）+ AppImage（评估）；对 GPL 依赖与发行版政策做打包审查。

**4.3.4 验证清单**：Wayland 合成器矩阵（KDE/GNOME/Hyprland/Sway）、Chrome/Electron 输入（启动参数提示页）、IBus 用户迁移说明、fcitx5 崩溃 core dump 符号化。

### 4.4 Android

**4.4.1 模块划分**：`:app`（主 App：设置/词库中心/vault/录音/组件下载）、`:keyboard`（IME UI）、`:core-binding`（openkey-ffi JNI）、`:voicepack`（引擎动态加载器）。

**4.4.2 IME**
- `OpenKeyIME : InputMethodService`；Compose 键盘 UI；候选条自绘。
- 密码框检测（`EditorInfo.inputType` 含 `TYPE_TEXT_VARIATION_PASSWORD`）：键盘内密码模式（工具条按钮）→ 解锁 vault → 匹配列表（按 App 包名/URI）→ 逐字 commitText（随机间隔）；普通文本框同。
- **AutofillService**：`OpenKeyAutofillService : AutofillService`（API 26+），实现 inline suggestions（Android 11+）渲染进本键盘候选条——"输入法本体即填充器"（调研报告 2.2 确认的整合先例空白）。
- 贴图：`commitContent`（探测 `contentMimeTypes`）→ 支持则以 InputContentInfo 提交；否则复制剪贴板 + Toast 引导。

**4.4.3 权限最小集**：IME 必备 + 网络（仅组件下载/同步/图床，均在对应功能开启后使用）+ 麦克风（语音功能开启后请求）；READ_CLIPBOARD 类权限不申请（Android 10+ 系统仅输入法豁免窗口期内读取，遵循系统行为）。

**4.4.4 分发**：官网直装 APK（v2/v3 签名）+ GitHub Releases；App 内更新检查（下载新 APK → 用户确认安装，未知来源安装引导页）；F-Droid 远期。

**4.4.5 语音组件动态加载（DR-004 关键实现）**
```
用户开启语音 → 检查 components_current(voice-engine-<abi>)
 → 无 → 展示组件说明（体积/用途/来源）→ 用户确认 → 下载 zip
 → SHA-256 校验 → 解压 filesDir/voicepacks/v1.10.0/ → System.load(绝对路径)
 → VoiceEngine 就绪；失败（ABI/损坏）→ 清理并回滚旧版本
键盘内使用：IME 进程直接加载（与主 App 下载的私有目录同一 uid 可读，注意多进程目录策略——下载固定在 :app 进程，键盘进程同 uid 可 System.load）
```
- so 依赖：组件包内自带 libc++_shared 与 onnxruntime（与 NDK 版本对齐并在 manifest 声明最低 NDK ABI）。

**4.4.6 验证清单**：主流 ROM 兼容（MIUI/ColorOS/HyperOS 的 IME 保活与权限差异）、密码框逐字键入在银行 App 的可用性抽样、commitContent 宿主支持矩阵（微信/QQ/Telegram/Keep）、内存（键盘进程常驻 ≤ 120MB）。

### 4.5 iOS

**4.5.1 结构**：单 App Group `group.app.openkey.shared`（主 App / KeyboardExt / CredentialProviderExt 三 target 共享 SQLite、词库、模型目录）。
- 主 App（SwiftUI）：设置/词库中心（下载/导入）/表情管理（上传转换管线）/vault/录音/组件下载/Full Access 引导。
- KeyboardExt：候选 UI + 本地功能（无 Full Access 状态下功能完整可用——审核 4.4.1）。
- CredentialProviderExt：`ASCredentialProviderViewController`（passkey iOS 17+ 声明）。

**4.5.2 内存预算（常驻目标 ≤ 40MB，峰值 ≤ 55MB）**

| 项 | 预算 |
|---|---|
| 键盘 UI 框架与视图 | ~12MB |
| 词库 mmap 常驻页（结构见 5.1） | ≤ 12MB |

**4.5.4 密码**

## 5. 功能模块行为规范（产品级）

### 5.1 基础拼音输入

- 候选条：横条、翻页（-/= 与左右键、移动端左右滑）、首页 5（可配 3–9）+ 表情/符号位；高频操作一致：Shift 中英、Ctrl+, 设置（桌面）。
- 双拼：自然码/小鹤/微软/智能 ABC（复用 rime schema 配置，词库中心提供）。
- 模糊音/错音纠正/简繁（OpenCC）：设置开关，随 rime 方案部署。
- 词库结构（mmap 友好）：`*.table.bin`（按音序排序的定长索引 + 变长词区）+ `prism.bin`；由 tools/ 词库构建器从 CC0 源生成，标注版本与哈希。

### 5.2 密码管理

- 入口：键盘工具条"钥匙"按钮（桌面为候选栏右侧图标）→ 未设置引导至设置 App；已设置 → 解锁（主密码/生物识别）。
- 匹配：当前 App 包名 / 窗口标题或剪贴板 URL → 匹配列表（精确 URI > 域名后缀 > 全部）；无匹配展示搜索。
- 键入：见 4.1.3 状态机（逐字、随机间隔、完成后 SoftLock）；剪贴板 TTL 45s 并显示倒计时。
- 自动锁定：Unlocked 60s 闲置 / 切后台即 SoftLocked（可配）；SoftLocked 生物识别重解；Locked 需主密码。
- 隐私铁律：密码模式期间暂停——用户词频学习、剪贴板记录、候选上报（本地学习开关在密码模式下强制关闭）；密码字段值永不出现在任何日志/同步通道（vault 同步仅经 Bitwarden 服务器或 E2E 密文）。
- 二期：TOTP 复制、附件（先跳过 Bitwarden attachments）。

### 5.3 云同步

- 首启向导：可选"稍后"，开启时引导填 WebDAV 地址/账号/密码（端到端加密口令第二步可跳过——跳过则 payload 明文仅 HTTPS 保护，UI 强提示）；设备命名。
- 同步范围开关：用户词库/自定义短语/表情元数据/剪贴板/设置——默认词库+短语+设置开、剪贴板关。
- 冲突呈现：合并自动进行，仅删除 vs 修改类冲突在"同步日志"页可见（30 天找回）。
- 状态可见性：各端设置页显示最近同步时间/结果/下轮计划。

### 5.4 图片表情

- 管理（主 App/设置 App）：添加图片（批量）→ 自动管线（缩放→gif→体积校验）→ 编辑关键字（多关键字空格分隔）→ 选择图床（未配置引导配置模板）→ 上传。
- 关键字命中：输入拼音命中关键字 → 候选条出现表情项（排序在第三位起，避免干扰文字候选）；点击按场景矩阵输出（1.2 表）。
- 未上传表情：仅本机可用（不上传则无远端 URL，链接路径不可用，界面明示）。
- 官方表情库：远期（Phase 7），客户端仅预留"聚合清单"加载接口。

### 5.5 语音输入

- 首启流程：开启语音 → 组件说明页（体积/来源/许可）→ 下载（进度条/断点续传）→ 就绪 → 15s 试音。

- AI 纠错设置：OpenAI 兼容端点（base URL/key/model）+ 开关；prompt 固化为"修正同音错字/标点/断句，保持口语，仅输出修正文本"；无端点时该功能隐藏。

### 5.6 词库中心与 CC0 内置词库

- 内置（DR-001，CC0/自制）：`openkey-base` 基础词库（一期目标：8105 规范汉字全表 + 6–10 万高频词条 + 地名/常用英文），由 tools 构建并随包分发；质量基准：对标 rime-ice 的基础词库做抽样评测（首屏命中率 ≥ 90%）。

## 6. 安全设计

### 6.1 威胁模型（摘要）

| 攻击面 | 威胁 | 对策 |
|---|---|---|
| 键盘进程（天然"受信 keylogger"争议） | 凭据经键盘 | 密码模式暂停一切学习/记录；核心路径（vault 解密→键入）代码走 fuzz + 审计 |
| vault 文件被拖走 | 离线暴力破解 | Argon2id（内存 64MB 档）+ 迭代下限；密文格式与 Bitwarden 一致 |
| 同步通道（WebDAV 运营方可信度低） | 服务端读取/篡改 | E2E 加密（GCM）+ manifest GPG 签名（服务端写入需签名私钥，被篡改即验签失败） |
| 组件下载（自行分发的供应链） | 恶意组件替换 | SHA-256 + manifest GPG 签名 + 客户端内置公钥指纹 + 不静默下载 |
| 图床上传 | 表情泄露指纹 | 上传产物经用户显式配置的图床；默认关闭；关键字不随图上传（不传 alt/remark 字段） |
| 密码模拟键入被滥用（对本产品） | 其他程序驱动 OpenKey 键入密码 | 键入动作必须源于键盘 UI 用户操作事件；TSF/SendInput 均校验来源进程；无外部 IPC 触发键入 |

### 6.2 密钥层级

```
主密码 ─KDF(Argon2id/PBKDF2)─▶ master key ─HKDF─▶ stretched master key
                                    │
                     ┌──────────────┼──────────────┐
                     ▼              ▼               ▼
                 vault user key  sync passphrase  组件校验公钥（内置指纹，非派生）
                     │              │
                     ▼              ▼
              vault 各条目加密   同步条目 E2E（AES-256-GCM）
OS 侧存储：user key 包裹件存 Keychain / Keystore(CryptoSettings) / CNG DPAPI / libsecret；
包裹密钥不出安全区；内存中 key 材料使用 zeroize 清零。
```

### 6.3 同步 E2E 细节

- sync passphrase 存在时：payload = `AES-256-GCM(key=HKDF(passphrase, salt=owner_hint), aad=key|kind|hlc)`；WebDAV 全盲文。
- 无 passphrase：仅 TLS；设置页红色警示"服务器可见明文"。
- 密钥轮换：导出重加密（新 passphrase 重新加密全量条目，作为一次快照操作）。

### 6.4 组件供应链

- 发布私钥离线保管；发布流程（7.4）：CI 产出 → 哈希 → 离线签名 manifest → 上传；客户端 `versions.json` 验签失败则拒绝并警示。
- 用户自定义镜像：镜像与官方 manifest 验签不一致时明确警示降级（允许用户选择信任镜像）。

4. AI 纠错管线（OpenAI 兼容端点）
验收：组件下载全端成功/失败路径演练；RTF 实测（中端 Android < 0.3）；AI 纠错超时降级路径

**Phase 7：官方云服务（远期，另立项）**
- 账号体系与托管同步 = `SyncBackend` 新实现；官方表情库清单；AI 托管管线。客户端代码已预留接口，不阻塞。

### 8.2 资源与并行建议

- **最小可行团队**：core（Rust）2 人、Windows 1 人、Apple 双端 1 人、Android 1 人、Linux 0.5 人（可与 core 合并）、测试/发布 1 人。Phase 1 是瓶颈（五端并行），若人力受限优先序：Android → Windows → iOS → macOS → Linux（按用户基数与验证价值）。
- 语音（Phase 6）依赖 Phase 0 组件基建，不依赖 Phase 2–5，可独立分叉推进。
- iOS 端虽然分发排最后（DR-002），**开发节奏与桌面同步**，避免架构验证滞后。

### 附录 C：图床模板 JSON Schema（字段定义）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` / `name` / `version` | string/int | 模板标识 |
| `request.method/url` | string | HTTP 方法与端点（支持 `{token}` 占位） |
| `request.headers` | object | 认证头模板（值支持 `{token}`、`{account}` 等） |
| `request.multipart[]` | array | 字段名与 `fromFile` 标记 |
| `response.urlPath/deletePath/errorPath` | string | JSONPath 提取 |
| `response.successWhen` | expr | 成功判定（`code == 200` 形式的受限表达式，白名单运算符） |
| `credential.fields[]` | array | 配置表单字段定义（token/password/text 类型） |

内置 provider（oss/cos/s3）使用独立配置 schema（bucket/region/endpoint/domain/pathPrefix），在设置 UI 渲染专属表单。
